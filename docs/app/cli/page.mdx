```
envi <command> [flags]
```

Every command that touches your account first checks for a stored session (`envi auth`), then talks to the API directly — the CLI never needs the web dashboard running.

## Authentication

### `envi auth`

Signs in. By default this is the browser device flow: it prints a code, opens your browser, and waits for you to approve it there.

```bash
envi auth
```

<ParamField query="--email" type="string">
  Skip the browser and sign in with an emailed one-time code instead. Prompts for the code interactively.
</ParamField>
<ParamField query="--no-browser" type="boolean">
  With the device flow, print the approval URL instead of trying to open a browser — useful over SSH.
</ParamField>

```bash
envi auth --email you@company.com
```

### `envi auth --key <key>`

Signs in with a [personal API key](#personal-api-keys) instead of the browser. Useful on a machine where opening a browser isn't practical, and in scripts.

```bash
envi auth --key envi_...
```

The key is traded for an ordinary session, which is what gets stored. The key itself is never written to disk.

### `envi logout`

Revokes the current device's session.

```bash
envi logout
```

## Project setup

### `envi init`

Links the current directory to a project and environment, writing `envi.toml`. Interactive if run with no flags.

<ParamField query="--project" type="string">Project name</ParamField>
<ParamField query="--env" type="string">Environment name</ParamField>

```bash
envi init --project acme-api --env production
```

### `envi project create <name>`

```bash
envi project create acme-api
```

## Environments

A project holds any number of environments. The CLI calls them **origins**, because from a working directory what matters is which one you are pointed at — the dashboard and the API call the same thing an environment.

### `envi origin list`

Lists the current project's origins, marking the one this directory is linked to.

```bash
envi origin list
```

```
* development
  production
```

### `envi origin switch <name>`

Repoints `envi.toml` at another origin and pulls its secrets into `.env`. If `.env` holds changes you have not pushed, the switch is refused rather than discarding them.

<ParamField query="--force" type="boolean">Overwrite unpushed local `.env` changes instead of refusing</ParamField>

```bash
envi origin switch production
```

`envi origin use` is an accepted alias.

### `envi origin create <name>`

Creates an origin under the current directory's project (from `envi.toml`). It does not switch to it.

<ParamField query="--project" type="string">Project name, if not using the current directory's `envi.toml`</ParamField>
<ParamField query="--production" type="boolean">Mark this origin as production</ParamField>

```bash
envi origin create staging
envi origin create production --production
```

`envi env create <name>` is an accepted alias, with the same flags.

## Working with secrets

These three all operate on the origin linked by `envi init` in the current directory, unless you name another one.

### `envi pull`

Writes the environment's current secrets to `.env`, at `0600` permissions.

```bash
envi pull
```

### `envi push [file] [origin <name>]`

Sends a local env file up. With no arguments it pushes `.env` to the origin this directory is linked to.

```bash
envi push
```

Name a file to push something other than `.env`:

```bash
envi push .env.test
```

Add `origin <name>` to write to a different origin without switching to it. Because that changes an origin you are not looking at, it prints what will change and waits for a yes:

```bash
envi push .env.test origin production
```

<ParamField query="--force" type="boolean">
  Push even though the remote has moved on since your last pull, overwriting it with your local file. It also answers the confirmation prompt, so a cross-origin push with `--force` runs unattended.
</ParamField>
<ParamField query="--yes" type="boolean">
  Answer the confirmation prompt, without forcing past a conflict.
</ParamField>
<ParamField query="--clean" type="boolean">
  Delete the file once the push succeeds, so a pull, edit and push cycle leaves nothing plaintext on disk. A failed push never deletes anything.
</ParamField>

```bash
envi pull          # write .env
# ...edit it...
envi push --clean  # send it up and remove the file
```

Without `--force`, a remote that changed since your last pull is rejected rather than overwritten:

```
remote secrets have changed since your last pull; run envi pull to take them,
or envi push --force to overwrite them with your local file
```

<Note>
  A push adds and updates the keys in the file it sends. It does not delete keys the file leaves out — remove those from the dashboard.
</Note>

### `envi diff`

Compares local `.env` against remote without changing either side. Prints `added`, `removed`, and `changed` keys.

```bash
envi diff
```

### `envi run -- <command>`

Runs a command with the origin's secrets in its environment, without writing a `.env` at all. This is the better default for most projects: the secrets live for as long as the process does and never touch the disk.

```bash
envi run -- npm start
envi run -- ./deploy.sh
```

Everything after `--` is the command, passed through untouched, including its own flags:

```bash
envi run -- npm run dev -- --port 3000
```

<ParamField query="--origin" type="string">
  Run against another origin for this one command. `envi.toml` is not changed.
</ParamField>
<ParamField query="--preserve-env" type="boolean">
  Keep the value already in your environment when a name exists in both. By default the secret wins.
</ParamField>

```bash
envi run --origin production -- ./migrate.sh
```

<Note>
  `envi run` exits with the status of the command it ran, not with one of Envi's own exit codes, so scripts wrapping a command in `envi run` see exactly what they would have seen without it. A command that cannot be found exits `127`; one killed by a signal exits `128` plus the signal number. Envi's own failures — not signed in, no `envi.toml`, API unreachable — all happen before the command starts.
</Note>

In CI or a container, set `ENVI_TOKEN` to a [service token](/ci-service-tokens) and `envi run` works with no `envi.toml` at all — the token names the environment. `ENVI_PROJECT` and `ENVI_ENVIRONMENT` say which to read when the credential isn't scoped to one. See [Docker](/docker).


### `envi mod`

Opens this origin's secrets in a full-screen editor. Edit them, press `^O` to push, and nothing is ever written to disk — no `.env` to create, forget, or clean up afterwards.

```bash
envi mod
```

| Key | Does |
|---|---|
| `^O` | Push the buffer back to Envi |
| `^X` | Leave; asks first if you changed anything |
| `^K` | Cut the current line |
| `^A` / `^E` | Start and end of line |
| Arrows | Move around |

The buffer is the same `KEY=VALUE` text `envi pull` writes, so what you edit here and what lands in a file are the same thing. Add a line to add a secret, delete one to remove it.

<ParamField query="--origin" type="string">
  Edit another origin instead of the linked one.
</ParamField>

Pushing uses the same conflict check as `envi push`. If someone else changed the environment while you were editing, the push is refused and the status bar says so, rather than overwriting their work.

<Note>
  `envi mod` needs an interactive terminal. In a script or a pipe it refuses and points at `envi pull` and `envi push` instead.
</Note>

## Collaboration

### `envi share <email>`

Invites a collaborator. They receive an email with a link — see [Invitations](/invitations) for what happens next, including for people who don't have an account yet.

<ParamField query="--project" type="string">Project name</ParamField>
<ParamField query="--env" type="string">Environment name</ParamField>
<ParamField query="--permission" type="string" default="read">`read`, `write`, or `manage`</ParamField>

```bash
envi share teammate@company.com --permission write
```

### `envi invite accept <token>`

Accepts an invitation using the token from an invitation link. You must already be signed in as the invited address — normally you'd just click the link instead, which handles this for you.

```bash
envi invite accept <token>
```

## Personal API keys

A key is your own credential, not a project's. It acts as you, across everything you can reach, up to the permission you give it. For a credential scoped to a single environment, use a [service token](/ci-service-tokens) instead.

### `envi key create --name <name>`

<ParamField query="--name" type="string" required>What the key is for, such as `laptop` or `ci`</ParamField>
<ParamField query="--permission" type="string" default="read">`read`, `write`, or `manage`. A `read` key cannot change anything; a `write` key can change secrets but cannot hand out access or create credentials.</ParamField>
<ParamField query="--days" type="int" default="90">Days until it expires. `0` never expires.</ParamField>

```bash
envi key create --name laptop --permission read
```

The key is printed once and never again, because only a hash of it is stored.

### `envi key list`

Your keys, with what each may do, when it expires, and when it was last used.

### `envi key revoke <id>`

Stops a key working. Any session started with it is signed out at the same time, so a leaked key stops being useful immediately rather than when its session happens to run out.

<Note>
  The permission on a key is a ceiling, not a grant. It never gives you access you don't already have, and the usual per-environment permissions still apply underneath it.
</Note>

## CI/CD

### `envi token create --name <name>`

Mints a scoped [service token](/ci-service-tokens) for the current directory's environment.

<ParamField query="--name" type="string" required>Token name</ParamField>
<ParamField query="--permission" type="string" default="read">`read`, `write`, or `manage`</ParamField>
<ParamField query="--ttl" type="int" default="0">Lifetime in seconds. `0` means no expiry.</ParamField>

```bash
envi token create --name github-actions --permission read --ttl 2592000
```

## Exit codes

Scripts checking `envi`'s exit status can distinguish failure kinds without parsing output:

| Code | Meaning |
|---|---|
| `0` | Success |
| `2` | Usage error — bad flags or arguments |
| `3` | Not authenticated |
| `4` | Forbidden — authenticated, but not permitted |
| `5` | Configuration error — e.g. not initialized, run `envi init` |
| `6` | API error |

## Updating

### `envi update check`

Reports whether a newer release exists, without changing anything.

### `envi update now`

Installs it. The route depends on how Envi was installed: a script install replaces its own binary after verifying the checksum, and a package-manager install hands over to `npm`, `bun`, `pnpm` or `yarn`, whichever owns it. Overwriting the file directly would leave the package manager still reporting the old version.

<ParamField query="--force" type="boolean">
  Update even from a development build, or when already current.
</ParamField>
