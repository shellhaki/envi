A key-value store for your project, read and written from code.

```bash
npm install @shellhaki/envi-sdk
```

```ts
import { Envi } from "@shellhaki/envi-sdk";

const envi = new Envi({ token: process.env.ENVI_TOKEN! });

await envi.set("THEME", "dark");
await envi.get("THEME");        // "dark"
```

## This is not your secrets

The two live side by side and are deliberately different things:

| | Secrets | Key-value store |
|---|---|---|
| Belongs to | One environment | The whole project |
| History | Every version kept | Current value only |
| Written by | You, through the CLI or dashboard | Your application, while it runs |
| Read by | `envi pull`, `envi run`, the dashboard | This SDK |
| Encrypted | Yes | Yes, same cipher |

Use secrets for the credentials your app needs to start: database URLs, API keys, signing keys. Use the key-value store for things your app decides while running — a feature flag, a cached setting, the last time a job ran.

<Note>
  Both are encrypted at rest with AES-256-GCM. The split is about lifecycle, not sensitivity: secrets are configuration you deploy, key-value entries are state your code owns.
</Note>

## Choosing a credential

### A service token, for anything deployed

A [service token](/ci-service-tokens) belongs to one environment, and the store belongs to the project that environment is in — so the token already knows which project to act on, and there's nothing else to configure:

```ts
const envi = new Envi({ token: process.env.ENVI_TOKEN! });
```

```bash
envi token create --name my-app --permission write
```

A `read` token can read the store but not write to it.

### A personal API key, while developing

An [API key](/cli#personal-api-keys) can reach every project you can, so it has to be told which one:

```ts
const envi = new Envi({
  apiKey: process.env.ENVI_API_KEY!,
  project: "acme-api",
});
```

A `read` key can read but not write, the same as a read-only token.

<Warning>
  The SDK is server-side only, and refuses to construct if `window` exists. A credential in browser code would ship to every visitor along with everything it can read. Read values on the server and pass down only what the page needs.
</Warning>

## The API

<ParamField query="await envi.get(key)" type="string | undefined">
  A value, or undefined if it isn't set. Loads the store on first use and reads from memory after that.
</ParamField>
<ParamField query="await envi.require(key)" type="string">
  The same, but throws `EnviMissingKeyError` naming the key. Useful at start-up, so a missing value fails immediately rather than at the first request that needs it.
</ParamField>
<ParamField query="await envi.set(key, value)" type="Promise<void>">
  Writes a value, replacing anything already under that key. Values are strings, up to 64KB.
</ParamField>
<ParamField query="await envi.delete(key)" type="Promise<void>">
  Removes a key. Deleting one that isn't there is not an error.
</ParamField>
<ParamField query="await envi.all()" type="Record<string, string>">
  Every value, as a plain object.
</ParamField>
<ParamField query="await envi.keys()" type="string[]">
  The keys currently set, sorted.
</ParamField>
<ParamField query="await envi.refresh()" type="Promise<void>">
  Fetches again, picking up changes made elsewhere.
</ParamField>
<ParamField query="envi.project" type="string">
  Which project these values belong to. Worth logging at boot to confirm a deploy is talking to what you think it is.
</ParamField>

Options also include `baseUrl` if you self-host, `timeoutMs` (default 10000), and `fetch` to supply your own.

## How reads and writes behave

The store is fetched **once**, on the first read, and held in memory. After that `get`, `all` and `keys` cost nothing and never touch the network. `set` and `delete` go to the server and update what's held, so a value you just wrote reads back immediately without another fetch.

Values changed elsewhere won't appear until you ask:

```ts
await envi.refresh();
```

There is no background polling and no timer, which matters on serverless platforms where a process can be frozen between requests.

## Failures

Each kind is its own error class, because the fix differs:

| Error | Means |
|---|---|
| `EnviAuthError` | The credential is missing, wrong, expired, revoked, or not allowed to write |
| `EnviNotFoundError` | No such project. The message lists what you can see |
| `EnviUnreachableError` | Envi could not be reached, or did not answer in time |
| `EnviMissingKeyError` | `require()` asked for a key that is not set |

```ts
import { Envi, EnviAuthError } from "@shellhaki/envi-sdk";

try {
  await envi.set("THEME", "dark");
} catch (error) {
  if (error instanceof EnviAuthError) {
    // a read-only token, or one that has been revoked
  }
  throw error;
}
```

## A complete example

```ts
import { Envi } from "@shellhaki/envi-sdk";

const envi = new Envi({ token: process.env.ENVI_TOKEN! });

export async function lastRun(): Promise<Date | null> {
  const value = await envi.get("JOB_LAST_RUN");
  return value ? new Date(value) : null;
}

export async function recordRun() {
  await envi.set("JOB_LAST_RUN", new Date().toISOString());
}
```

## Where this fits

- Secrets your app needs at boot: [`envi run`](/cli) injects them with no code and no dependency, or the dashboard shows them.
- On Vercel, Netlify, Lambda or Cloudflare Workers you can't wrap the process, so `envi run` is not an option — set one credential in the platform's own secret store and read the rest from here.
- The SDK still needs that one credential in the environment. It turns many values into one, which is the same trade `envi run` makes.
